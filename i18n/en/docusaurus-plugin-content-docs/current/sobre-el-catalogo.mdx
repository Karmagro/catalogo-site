# About the Catalog

The Component Catalog is a browsable collection of twenty-two recurring software components that appear in information systems. Each component is documented with a consistent structure of eleven fields, which makes it possible to understand what it does, how it relates to other components, and which parts of the Digital Board it materializes.

## What is a component? {/* #que-es-un-componente */}

<div className={styles.keyConcept}>
  <div className={styles.keyConceptLabel}>Working definition</div>
  <div className={styles.keyConceptText}>A component is a <strong>type of recurring functionality defined by its purpose</strong>, not by its technical implementation. A "Data Manager" serves the same purpose whether it is implemented in Java, Python, or any other technology: managing the life cycle of a data entity through create, read, update, and delete operations.</div>
</div>

This distinguishes the components of the catalog from other meanings of the term in software engineering (such as the components of the C4 model, which describe groupings of code within a container). The components of the catalog operate at the functional level, close to software requirements, and are understandable to both developers and business stakeholders.

The distinction between mandatory and additional capabilities (fields 3 and 4) is particularly important: it makes it possible to recognize the same component in systems with different degrees of sophistication. A basic Data Manager offers listing, creating, editing, and deleting records; a more advanced one may also include export, advanced filters, or sorting by column. Both are instances of the same component, but with different additional capabilities.

## Relationship with the Digital Board {/* #relacion-con-el-tablero-digital */}

The catalog and the Digital Board are complementary tools that operate on different planes.

A single component can touch several sections of the board at once. For example, a Data Manager always involves Manual Update (creation and editing forms), Data Concepts (the entity it manages), and On-Demand Outputs (listing and searching records). This cross-cutting nature is a fundamental property of the catalog: components do not belong to a single section of the board.

The mapping between components and sections is presented in the [consolidated matrix](/docs/secciones) and in the individual sheet of each component.

## What the catalog is not {/* #lo-que-el-catalogo-no-es */}

:::caution[Setting expectations]

It is as important to understand what the catalog offers as what it does **not** offer:

- **It is not an implementation manual.** It does not indicate how to build a component in a specific language or framework.
- **It is not a catalog of design patterns.** It does not prescribe code structures or architectural solutions.
- **It is not exhaustive.** It represents a bounded set of components identified as recurring. Projects may require functionality that does not correspond to any component in the catalog.

:::

## Construction and validation {/* #construccion-y-validacion */}

The catalog was built through an iterative process that combined prior knowledge of information system development, observation of existing systems in academic and industrial contexts, consultation of technical references and specialized literature, and empirical validation through the detailed analysis of real information systems.

Each component was successively refined to delimit its essential characteristics, distinguish it from similar components, and document its typical dependencies.
